# Database — VELARIS

## 1. Storage model
Provider: Supabase-managed PostgreSQL + Prisma, with pgvector proposed for initial vector retrieval and subject to project/extension verification. Ownership model: platform → enterprise organization → tenant/company; the tenant/company is the primary data-isolation boundary in V1. Redis is for cache/queues, not the authoritative domain store.

## 3. Schema
Proposed baseline fields and constraints; exact Prisma schema and field types are implementation deliverables. IDs should use UUIDs unless a documented decision selects otherwise.

- `enterprise_organizations(id, name, status, created_at, updated_at)`; name required, status enum, unique constraints only where product rules require.
- `tenants(id, enterprise_organization_id, name, slug, status, created_at, updated_at, version)`; unique slug policy to be decided globally vs per enterprise; status rechecked for every operation/job.
- `users(id, external_subject, email_normalized, display_name, avatar_data_url, password_reset_required, token_invalid_before, status, created_at, updated_at)`; external subject unique per provider; email verification and provider constraints handled by identity decision. `avatar_data_url` stores a browser-compressed image data URL (at most 512 KiB decoded, PNG/JPEG/WebP, magic bytes checked), an empty string records an explicit removal, and NULL means the caller never changed the photo. No remote image URL is stored. `password_reset_required` blocks normal routes until a password change. `token_invalid_before` refuses access tokens issued at or before a password change or global session revocation.
- `tenant_memberships(id, tenant_id, user_id, status, created_at, updated_at)`; unique `(tenant_id,user_id)`; tenant and user FKs; tenant-scoped lookup index; created time plus id, and status plus created time plus id, for the platform directory page (migration `0023_platform_directory_page`, D-87).
- `roles(id, tenant_id nullable, code, name, system_managed, base_role_code, created_at)`; system roles and tenant-custom roles separated by constraints; role code unique in scope. A tenant-owned role uses `base_role_code` to inherit one canonical assignable permission profile, and system roles are read-only.
- `permissions(id, code, description)`; unique code; seeded/version-controlled.
- `role_permissions(role_id, permission_id)`; unique pair.
- `membership_roles(membership_id, role_id)`; unique pair and scope validation.
- `customers(id, tenant_id, external_ref nullable, display_name, email nullable, phone nullable, metadata_json, created_at, updated_at, deleted_at nullable)`; indexes by tenant and normalized lookup fields, plus tenant and created time for the paged customer list (migration `0022_list_read_indexes`, D-86); avoid unrestricted metadata secrets.
- `conversations(id, tenant_id, customer_id, channel, status, created_at, updated_at, version)`; tenant/customer composite ownership checks; tenant + updated time index, and a tenant/customer/updated time index that serves the customer page in read order (migration `0020_paged_list_indexes`, D-84).
- `messages(id, tenant_id, conversation_id, author_type, author_id nullable, visibility, body, metadata_json, idempotency_key nullable, created_at)`; `visibility` distinguishes customer-visible from internal; tenant/conversation/time index; unique idempotency scope where used.
- `tickets(id, tenant_id, customer_id, primary_conversation_id nullable, title, status, priority, sla_state, assignee_membership_id nullable, tags, version, created_at, updated_at, resolved_at nullable, closed_at nullable)`; valid status enum; status and assignee indexes that end with updated time, so a filtered page reads in order (migration `0021_queue_filter_indexes`, D-85), plus tenant/customer/updated time for the customer page (migration `0020_paged_list_indexes`, D-84); optimistic concurrency through version.
- `ticket_assignments(id, tenant_id, ticket_id, from_membership_id nullable, to_membership_id nullable, actor_id nullable, reason nullable, created_at)`; append history, tenant/ticket/time index. Membership ids are deliberately not foreign keys, so history survives a membership deletion; ticket deletion cascades (migration `0013_ticket_assignments`).
- `knowledge_sources(id, tenant_id, source_type, source_uri nullable, object_key nullable, status, content_hash, provenance_json, error_code nullable, created_by, created_at, updated_at, deleted_at nullable, retention_days nullable, expires_at nullable)`; unique tenant/source/content identity as appropriate; status and tenant/expiry indexes. A source past `expires_at` is unavailable at once, and the sweep marks it deleted and removes its chunks (migration `0007_retention_lifecycle`, T5.02).
- `knowledge_chunks(id, tenant_id, source_id, chunk_index, content, metadata_json, token_count, created_at)`; unique `(source_id,chunk_index)`; tenant/source index.
- `knowledge_embeddings(id, tenant_id, chunk_id, embedding vector, model, dimensions, created_at)`; unique chunk/model version; vector index chosen after query benchmark; filter by tenant and permission metadata before returning content.
- `ai_agents(id, tenant_id, name, description, status, owner_membership_id, active_version_id nullable, created_at, updated_at)`; tenant/name index.
- `ai_agent_versions(id, tenant_id, agent_id, version, config_json, created_by, created_at, published_at nullable, status)`; unique `(agent_id,version)`; published versions immutable.
- `ai_tool_definitions(id, tenant_id nullable, name, input_schema_json, output_schema_json, required_permission, risk_level, approval_required, timeout_ms, retry_policy_json, enabled)`; unique name in scope; schemas validated on registration.
- `agent_tool_grants(id, tenant_id, agent_version_id, tool_id, granted_by, created_at)`; unique version/tool; execution rechecks current authorization. `tool_id` carries a foreign key to `ai_tool_definitions` since migration `0006_tool_definitions` (T4.04), so a grant cannot name an unregistered tool.
- `tool_approval_requests(id, tenant_id, tool_definition_id, agent_version_id, proposal_hash, proposal_json, requested_by, status, decided_by, decided_at, expires_at, consumed_at, created_at)` (T4.04); a proposal that needs approval never executes while the row is PENDING, REJECTED or EXPIRED, and an APPROVED row is claimed once by a conditional update. Deciding needs `ai.tool.approve`.
- `ai_workflows(id, tenant_id, name, version, trigger_json, nodes_json, guardrails_json, enabled, created_at)`; unique tenant/name/version.
- `evaluation_runs(id, tenant_id, agent_version_id, dataset_version, provider, model, status, aggregate_json, failure_reasons_json, created_at, completed_at nullable)`; `dataset_version` names an immutable dataset object in `packages/ai-evals` (D-21), `aggregate_json` holds the case summary and `failure_reasons_json` the failed cases with severity, which the publish gate reads (T4.05). A run belongs to one agent version, so a run for an older version is never evidence for a new one.
- `ai_traces(id, tenant_id, correlation_id, agent_id, agent_version_id, provider, model, outcome, latency_ms, usage_json, spans_metadata_json, created_at, expires_at)`; avoid raw secrets and minimize message content. Every AI run writes one row through `AiTraceService` (T5.06, D-31). `expires_at` comes from the tenant TRACES retention policy, with a 30-day default when the tenant has none. Message text and document content never enter a row.
- `audit_events(id, tenant_id nullable, scope_key, actor_id nullable, actor_snapshot nullable, snapshot_version, action, resource_type, resource_id, metadata_json, request_id, chain_seq, prev_hash, event_hash, created_at)`, partitioned by month on `created_at`; append-oriented, restricted; index tenant/time, tenant/action/time for the action-filtered page (migration `0022_list_read_indexes`, D-86) and resource/time.
- `revoked_access_tokens(token_hash char(64) primary key, session_id varchar(64) nullable, expires_at, revoked_at)`; written by `POST /auth/signout` (D-51). Only a SHA-256 digest is stored, never the bearer token. `session_id` is indexed so a second access token from the same Supabase session is denied; `expires_at` bounds retention and is checked by the guard.
- `step_up_grants(id, subject, session_id, tenant_id nullable, action, token_hash char(64) unique, expires_at, used_at nullable, revoked_at nullable, created_at)`; written by `POST /auth/step-up` (T6.08, D-58). Only a SHA-256 digest is stored. A grant is bound to the identity subject, Supabase session, tenant and action, expires within 10 minutes, and `used_at` makes it single use. Indexes cover subject/action/expiry, session and expiry.
- `integration_endpoints(id, tenant_id, provider, display_name, secret_ref, status, created_at, updated_at)`; unique `(tenant_id, provider, display_name)`. `secret_ref` names an environment variable and never holds the secret value itself (D-30, migration `0008_webhook_integrations`, T5.05).
- `ai_model_providers(id, name, provider, model, base_url nullable, api_key_ref, is_default, status, created_at, updated_at)`; unique `name`, index on `is_default`. `api_key_ref` is an uppercase environment-variable name, never a credential value. The service clears the previous default and sets the new one in one transaction, so normal writes leave one default; migration `0012_ai_model_providers` creates the table (D-55).
- `webhook_deliveries(id, endpoint_id, tenant_id, provider, delivery_id, payload_hash, status, received_at)`; unique `(endpoint_id, delivery_id)` and a tenant/time index. A repeat with the same `payload_hash` writes nothing and repeats no side effect; the same delivery id with another hash is a 409 (TH-08, T5.05).
- `outbox_events(id, tenant_id nullable, event_type, schema_version, payload_json, correlation_id, occurred_at, published_at nullable, attempts)`; indexed unpublished events.
- `kpi_snapshots(id, tenant_id nullable, metric_code, formula_version, period_start, period_end, dimensions_json, value_numeric, calculated_at)`; unique metric/scope/period/dimension hash.
- `ai_memories(id, tenant_id, customer_id nullable, scope, content, provenance_json, confidence, permission_scope_json, created_at, expires_at, deleted_at nullable)`; opt-in, tenant-filtered, expiring and source-deletion-aware.
- `retention_policies(id, tenant_id, category, retention_days, updated_by nullable, created_at, updated_at)`; unique `(tenant_id, category)`; `retention_days` is 1..3650 by API validation and a CHECK (AC-F14-2, T5.02). Provisioning seeds one `TRACES` row per tenant with the 30-day default, and migration `0009_retention_policy_defaults` backfills existing tenants (T6.06, D-38). No `KNOWLEDGE` or `MEMORY` row is seeded.

## 4. Relationships and delete behavior
- EnterpriseOrganization has many Tenants; tenant deletion is a lifecycle workflow, not an uncontrolled cascade.
- Tenant owns memberships, customers, conversations, tickets, knowledge, agents, integrations, traces and tenant audit events. Tenant scoping is explicit on each tenant-owned record even where derivable through a parent.
- Customer has many Conversations and Tickets; Conversation has many Messages and may be associated with a Ticket. A conversation may exist without a ticket.
- Ticket has assignment history and timeline events; ticket status changes preserve audit/timeline history.
- KnowledgeSource has many KnowledgeChunks; chunks have embeddings. Source deletion invalidates/removes chunks, vectors, cache entries and derived references.
- AiAgent has many immutable AiAgentVersions; each version references explicit tool grants/workflow configuration and evaluation runs.
- Audit events are retained under policy and must not be silently cascaded away to conceal actions. Tenant deletion may require anonymization or controlled retention rather than hard delete.
- Idempotency records and outbox events use bounded cleanup after the retry/replay window.

## 5. Access rules
Authoritative matrix is `docs/SECURITY.md` section 3. Every tenant-owned table has a tenant ID or enforceable tenant ownership path; application repository methods require a `TenantContext`. Cross-tenant constraints should be reinforced with composite foreign keys/unique keys where practical. Supabase PostgreSQL Row Level Security (RLS) is a defense-in-depth control to configure and test, not a substitute for service-level authorization. Database service accounts use least privilege. Production data access and migrations require explicit owner approval.

## 5A. Supabase-specific operational requirements
- Treat Supabase as managed PostgreSQL, not as a reason to move authorization into the browser. Supabase Auth is the selected identity/session provider, but NestJS remains the authoritative authorization layer. Supabase Auth is the selected identity/session provider, but NestJS remains the authoritative authorization layer.
- Decide explicitly whether application requests connect through NestJS only (recommended for the initial architecture) or whether any client-side direct database access is required. Default: domain/business writes go through NestJS APIs.
- If direct client access is later approved, require authenticated identity, carefully designed RLS policies, least-privilege grants and automated cross-tenant negative tests for every exposed table/view/function.
- Keep service-role credentials server-only; do not use service-role access for end-user requests without application authorization checks.
- Separate migration credentials/process from normal runtime access where feasible. Verify pooler mode and prepared-statement compatibility for Prisma in the chosen deployment.
- Confirm pgvector extension support, vector dimensions, index strategy, tenant/permission filtering, connection limits, region, backups and restore process in the actual Supabase project.
- RLS policy changes are security-sensitive migrations and require security-agent review plus human approval before production rollout.

## 6. Queries and indexes
| Query (filter, sort, pagination) | Index | Reason |
| --- | --- | --- |
| Tenant tickets by status and updated time | `(tenant_id,status,updated_at DESC,id)` | Inbox and deterministic pagination |
| Tickets assigned to membership | `(tenant_id,assignee_membership_id,status,updated_at DESC)` | Assigned-to-me queue |
| Conversation timeline | `(tenant_id,conversation_id,created_at,id)` | Stable chronological history |
| Messages idempotency lookup | Unique `(tenant_id,conversation_id,idempotency_key)` when key supplied | Prevent duplicate message side effects |
| Tenant membership by user | Unique `(tenant_id,user_id)` and index `(user_id,status)` | Tenant context resolution |
| Knowledge chunks by source | Unique `(source_id,chunk_index)` | Re-indexing and source lifecycle |
| Vector similarity search | pgvector index plus mandatory tenant/permission filters | Retrieval performance without scope leakage |
| Audit events by tenant/time | `(tenant_id,created_at DESC,id)` | Restricted audit browsing |
| AI traces by correlation ID | `(correlation_id)` and `(tenant_id,created_at DESC)` | Debugging and operations |
| Revoked token/session lookup | primary key `(token_hash)`, index `(session_id)`, index `(expires_at)` | Per-request sign-out denial without retaining raw credentials |
| Pending outbox jobs | `(published_at,occurred_at)` partial index for unpublished events | Reliable event dispatch |
| Inbox queue search (title, customer text, customer name and email) | pg_trgm GIN on `tickets(title)`, `messages(body)` partial on customer-visible CUSTOMER rows, `customers(display_name)` and `customers(email)` | Case-insensitive `contains` without a full scan; the partial predicate keeps internal notes out (D-80) |

Pagination must have maximum page size, stable ordering and tenant scope. Cursor pagination is preferred for high-volume timelines/feeds where offset pagination degrades.
